# NVIDIA source lead: power-sensor simulator

NVIDIA's Linux open kernel source tag `610.57.04` (commit `e4a5faa2567f28c8eabe0ebb6422b6d0abcf37eb`) declares a GPU Performance Scaling control and enumerates power-sensor simulator state/data subcommands in [`ctrl0000system.h`](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/e4a5faa2567f28c8eabe0ebb6422b6d0abcf37eb/src/common/sdk/nvidia/inc/ctrl/ctrl0000/ctrl0000system.h). The same header also declares similar subcommands under a PFM request-handler interface.

This is a **research lead**, not an established fix. These are interface declarations for a nearby Linux driver release, not proof that Windows 610.62 implements them, that a GeForce laptop exposes them, that they affect the GPU's hardware power-cap loop, or that they would be safe or effective. The follow-up implementation findings below weaken the lead for the inspected Linux release; code outside that boundary or firmware may differ.

A broader source search found a Linux ACPI-notification caller in [`osapi.c`](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/e4a5faa2567f28c8eabe0ebb6422b6d0abcf37eb/src/nvidia/arch/nvalloc/unix/src/osapi.c). Following that caller revealed a material limitation: in this source release [`cliresCtrlCmdSystemGpsControl_IMPL`](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/e4a5faa2567f28c8eabe0ebb6422b6d0abcf37eb/src/nvidia/src/kernel/rmapi/client_resource.c) immediately returns `NV_OK` without using the parameters. An apparent success from this particular implementation would not demonstrate a functioning simulator.

The same `client_resource.c` dispatches the separate PFM request-handler control to `pfmreqhndlrControl`. Its [`_PfmreqhndlrControlTable`](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/e4a5faa2567f28c8eabe0ebb6422b6d0abcf37eb/src/nvidia/src/kernel/platform/platform_request_handler_ctrl.c) contains only the supported-functions query and the SBIOS initialization/acknowledgement command; unmatched commands return `NV_ERR_NOT_SUPPORTED`. The declared simulator subcommands therefore have no handler in that implementation. These findings concern the inspected Linux source and cannot establish the behavior of Windows 610.62, but they substantially weaken this as an actionable simulator route. No simulator calls were made.

Before considering any simulator write, determine which resource-manager path and GPU power domain the current machine actually uses, whether a supported read-only query can establish feature availability, and what independent power/thermal safeguards and rollback are available. A user-mode NVML display change alone would not prove that the power controller consumed a different reading. No simulator command was sent.

## Installed Windows 610.62: matching dispatch entry is a success stub

Offline PE inspection of the installed `nvlddmkm.sys` (SHA-256 `a5dde035859cfa298f890c832ae3094002b13a24462ace190da8c2c85ae46142`) found a 32-byte `.rdata` record at RVA `0xe60940`: command `0x122`, parameter size `0x8`, common pointer `0x140e60710`, function pointer `0x140006170`, and final field `0x8`. Adjacent records contain command values `0x120`, `0x121`, `0x123`, etc. The command and size match NVIDIA's root GPS control definition (`NV0000_CTRL_CMD_SYSTEM_GPS_CONTROL`, eight-byte parameter structure) and the surrounding records have a dispatch-table pattern; this correspondence is strong static evidence but has not been verified through a runtime call.

At RVA `0x6170` the target consists of `xor eax, eax; ret` (bytes `33 c0 c3`). It neither reads the GPS subcommand nor the parameters. Thus, if this matching record is used for the GPS control, this driver route simply returns zero and cannot implement power-sensor simulation through that handler. This parallels the inspected Linux source stub. No RM command was sent and no settings were changed. It does not exclude other Windows interfaces or firmware-level mechanisms, and a zero return from this stub would not prove an action occurred.

The archived 461.92 driver has a matching `0x122`, size `0x8` table record at RVA `0x8a4df0`, pointing to RVA `0x727a10`, which is not the same immediate return stub. The old handler contains checks and additional indirect work. Its semantics and whether it receives this control on this device are unverified; its existence does not demonstrate a simulator or an applicable modern-driver fix.

## Installed Windows 610.62: separate PFM route

The same Windows root control table has a record at RVA `0xe60c60` for command `0x140`, size `0x8`, target RVA `0x2c2320`, matching the PFM request-handler control in the NVIDIA header. Static disassembly of the target shows a loop over request entries and a call to RVA `0x402430` for each. That function searches a 16-byte-entry table at RVA `0x11a5730`; the observed entries are subcommands `0x010e` and `0x0320`, followed by a null-handler terminator. A nonmatching subcommand returns `0x56`; the outer routine writes `0x80000000` for unsuccessful requests.

The published header names the four PFM power-simulator subcommands `0x0250` through `0x0253`. None appears in the Windows dispatch table above. This is strong evidence that the matching PFM route, as statically implemented in installed 610.62, does not dispatch those simulator commands. The Linux source has the corresponding two supported entries. This does not rule out undocumented controls outside this dispatch table. No request was sent to the driver.

## GSP mode query on the live GPU

On 8 November a read-only call to NVIDIA's documented `nvmlDeviceGetGspFirmwareMode` returned status 3 (`NVML_ERROR_NOT_SUPPORTED`) after successful NVML initialization and GPU-handle lookup. The output parameters were not treated as valid. NVIDIA's [current API reference](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html) documents this query, while documentation across releases differs in how it describes unsupported results. This result, together with `nvidia-smi` showing GSP firmware version `N/A`, does not identify where the GPU's power-control loop runs or establish that all GPU firmware is absent. No settings were changed.

A separate read-only query used NVIDIA's documented `NvAPI_GPU_GetGspFeatures`, interface ID `0x581c4391`, after successful NVAPI initialization and enumeration of one physical NVIDIA GPU. It passed a version-1 `NV_GPU_GSP_INFO` structure, sized according to NVIDIA's public headers, and returned `-104` (`NVAPI_NOT_SUPPORTED`); the output firmware string was not treated as valid. NVIDIA [documents this function](https://docs.nvidia.com/nvapi/group__gpu.html) as returning not-supported when GSP is not running. This is stronger reported evidence against an active GSP than `N/A` alone, subject to the installed driver's implementation and API contract. GSP is not the same as the GPU's separate PMU or other firmware, so this result does not locate the power-control loop, explain the false reading, or establish a 90 W injection point. NVAPI was unloaded and no setting changed.
