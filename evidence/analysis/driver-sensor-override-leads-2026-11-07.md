# Installed-driver sensor override leads — 7 November 2026

## Scope

Read-only static inspection of the installed Windows 610.62 `nvlddmkm.sys`, SHA-256 `a5dde035859cfa298f890c832ae3094002b13a24462ace190da8c2c85ae46142`. These identifiers are undocumented and their names alone do not establish what they affect on this GPU. No override was set and no driver, registry, firmware, or hardware state was changed.

## Performance-control sensor override

The ASCII string `RmPerfCfPmSensorOverrides` is at RVA `0xd14040`. A RIP-relative reference at RVA `0x4bb340` passes its address and a stack output location to a shared helper at `0x169380`. In the containing function (RVA range `0x4bae2a`–`0x4bb5a3`), execution can reach this reference only after several object/flag checks. On a zero return, the next instructions test bits 0 and 1 of the returned 32-bit value: bit 0 sets a local flag; otherwise bit 1 sets a byte at an object offset. The subsequent loop, when the local flag is set, conditionally calls an indirect object method for entries whose type byte is in the range 2–5. The types, object, indirect method, value source and real-world effects are not identified; do not infer that it corrects the reported watts or preserves any power limit.

The helper at `0x169380` calls routines with the name and output buffer. Other call sites use similarly named configuration strings. This is evidence for a potentially relevant configuration path, not yet a documented or tested registry setting. The matching GPU's Windows device-class registry key did not contain values beginning `RmPerfCf` or `RmPmgrIsense` when inspected; this does not exclude other registry locations, defaults, caches or active firmware settings.

### Follow-up: likely removal rather than fixed-value injection

Further static tracing of the installed, hash-identified driver found that the containing routine enters at `0x4badc0` and takes its group pointer in `r8`, later kept in `rdi`. Its initialization calls `0x6937e0` → `0x5a3900` → `0x277aa0`; the last initializer places the address of `0x277c50` in the group object's `+0x48` slot. In the bit-0 override path, the loop for types 2–5 calls the method in that slot with an entry index. The initialized target at `0x277c50` retrieves the indexed entry, makes an indirect call through that entry, clears the entry pointer, and updates associated index-tracking state. This is consistent with removing entries, not writing a wattage into them.

This is a static inference: other calls between initialization and use might replace the method pointer, the entry classes are still unknown, and actual execution was not observed. Nonetheless it makes blindly setting bit 0 a poor candidate for the requested constant 90 W input; it could remove sensor objects rather than supply a replacement. Bit 1's effect and the controller's actual data source remain unidentified. No settings were changed.

Offline follow-up traced the group population through `0x5f25c0` and parser `0x5efc00` to factory `0x4bb5d0`. The factory dispatches on an input byte 0–5 using a six-entry jump table at `0x4bb6e8`; these branches call constructors at `0x8cfe90`, `0x8d03d0`, `0x8d0910`, `0x8d0f20`, `0x8d1650`, and `0x8d1fa0`, respectively. Each constructor sets a corresponding one-hot bit (1 through 0x20) before calling common routine `0x4ba5c0`. This identifies concrete constructors for the four classes affected by the bit-0 range 2–5, but their meanings, the active types, and their relationship to board-power feedback remain unknown. The NVIDIA 610.57.04 public source snapshot has no matching names or constructor diagnostic IDs. The next static test would be to trace the methods installed by these four constructors to their data sources, rather than treat the names as proof of wattage sensing. None of these routines was invoked or modified.

For bit 1, the same routine stores `1` into the byte at object offset `0x2f8`. Offline inspection found a nearby routine at `0x4bacf0` that reads the same offset and forwards a true/false byte in `r8b` to an indirect method loaded from object offset `0x2a0`. A possible direct caller at `0x76894d` calls this routine. The shared layout and nearby code make these plausible producer/consumer sites for the bit-1 flag, but neither object identity nor the indirect method is resolved, and this has not been observed at runtime. The flag is not a 90 W value; its effect on sensor data or boost is unknown.

The candidate call chain extends from direct caller `0x76b664` through wrapper `0x768940` to `0x4bacf0`. After that call, the first routine can read a separate `RmPerfVideTestCtrl` configuration string and pass a small formatted buffer to another routine. This proximity is not enough to identify the object, the indirect method, or the power-control path. In particular, neither the separate string nor the boolean provides evidence of a usable 90 W override; no value was written.

The initialization wrapper at `0x7684d0` now provides a stronger static link: it passes its `rdx` object unchanged to `0x4badc0` and passes a group at that object's `+0x578` as the third argument. The later wrapper `0x768940` passes the same-shaped object and the same `+0x578` group to `0x4bacf0`. In the initializer, the bit-1 write at `0x4bb3ed` targets the unchanged second argument plus `0x2f8`; in the later function, the conditional at `0x4bacf4` reads the second argument plus `0x2f8`. These wrapper relationships are consistent with the later function consuming the flag in the same parent object. They still do not establish that these calls occurred for the live GPU, resolve the method at `+0x2a0`, or identify a wattage injection mechanism.

### Conditional candidate for the bit-1 method

The driver metadata adjacent to the initializer's method table includes class ID `0xed0b65`, named `Perf` in the nearby open-source release's `g_eng_desc_nvoc.h`. In the installed binary, a constructor associated with that metadata calls `0x17b58b0`, which conditionally populates the parent object's `+0x2a0` method slot. Static code shows at least two candidates: `0xa6fc40` for certain internal selector values and `0x6170` (immediate success return) for the fallback. Which is chosen on this GPU is not observed.

At `0xa6fc40`, the incoming boolean selects whether bit 0 is set or cleared in a 32-bit value obtained through an indirect object method with argument `0x350`; the modified value is passed to another indirect method, and similar operations occur in a loop over additional objects. The meaning of the object, argument, bit, and operations is not established: do not assume `0x350` is a GPU hardware register or that this controls board power. The candidate path changes a bit rather than directly accepting `90000` mW. This narrows the 90 W spoof investigation but does not establish the runtime target, sensor behavior, or a safe setting. No driver state was modified.

### GPU-family selector comparison

The constructor resolves class ID `0x74bc71`; NVIDIA's nearby open-source generated header names that class `GpuHalspecOwner`, with a `ChipHal` selector at the corresponding `+0x10` offset. A read-only call to NVIDIA's public `NvAPI_GPU_GetArchInfo` returned architecture `0x170`, implementation `0x6`, revision `0xa1` for the live GPU. NVIDIA's open source maps architecture `0x17`, implementation `0x6` to GA106 and selector index `46` (`0x2e`). Independent static inspection of the installed Windows driver's mapping routine found a matching `0x17`/`0x6` → `0x2e` branch. Sources: [NVIDIA NVAPI header](https://github.com/NVIDIA/nvapi/blob/main/nvapi.h) and [NVIDIA generated chip mapping](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/610.57.04/src/nvidia/generated/g_chips2halspec_nvoc.c).

If the same `GpuHalspecOwner` instance passed to the `Perf` method initializer carries index `46` on this GPU, the conditional at `0x17b6dd6` selects the `0x6170` immediate-success stub for the `+0x2a0` method rather than the bit-toggling implementation. The NVAPI query and matching static mappings make that a well-supported hypothesis, but no live kernel object or method pointer was observed. NVAPI's `0x170` representation and the internal `0x17` mapping are correlated, not directly traced in this execution. Consequently the bit-1 setting may be a no-op on this machine, but that is not established and no configuration was changed.

### Follow-up: driver registry lookup path

Read-only disassembly of the same hashed binary shows that helper `0x169380` first calls `0xebff0`; if that returns nonzero, it calls an alternate routine at `0x3169a0`. The first routine converts the supplied byte-string name to a wide string and passes it through `0x18f0f10` to `0x18f1320`. At `0x18f1364` the latter calls the imported `IoOpenDeviceRegistryKey` with key type `2` and access mask `0x20019`; these correspond to the device's driver-specific software key and read access under the Windows driver API. See [Microsoft's device registry API](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-ioopendeviceregistrykey) and [registry access rights](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights). This is static call-path evidence only: the device object, lookup result, alternate routine, and whether the sensor-override caller executes on this machine were not observed at runtime. It does not establish an effective setting or any safe value. No registry values were changed.

## Current-sense calibration names

The same binary includes `RmPmgrIsenseDiffGainOverride`, `RmPmgrIsenseDiffOffsetOverride`, `RmPmgrIsenseDiffCoarseGainOverride`, `RmPmgrIsenseVcmOffsetOverride`, `RmPmgrIsenseVcmCoarseOffsetOverride` and `RmPmgrIsenseCheckIgnore`. The gain string at RVA `0xd2dac0` is referenced at `0xbe7812` and `0xbe839e` in two separate functions. Each observed path has earlier object-state checks, calls the same `0x169380` helper, and on success masks the returned value to five bits before storing it in an internal object and setting a flag. Nearby code subsequently calls other functions; the physical sensor, units, encoding, supported GPU, and eventual effects are not established.

These paths deserve further tracing because they may be closer to power-control configuration than the NVML display page. They are not evidence of a safe value, a confirmed fault in any sense circuit, or proof that either path runs on this GPU. Blindly adjusting gains, offsets, sensor lists, or check bypasses could also change real power protection. Further work should identify the underlying object and initialization gates, trace the values into any firmware or hardware consumer, and obtain an independent power measurement before considering an intervention.


The `0xbe7360` function also handles names referring to hardware speedo, IDDQ and minimum SRAM voltage in the same initialization routine. That context raises the possibility that these `Isense` options concern on-chip characterization or calibration rather than the board-power sensor responsible for the reported wattage; the static evidence does not identify their domain. This substantially limits their value as a proposed fix until the object and hardware path are identified.

## Other power-manager override names

A fresh static string and reference scan of the same installed driver located `RmPmgrOverride` at RVA `0xd1a350`, referenced at `0x785771`. The observed code reads a 32-bit value through helper `0x169380` and stores it at an object's `+0x4ec4` offset when the lookup succeeds. The meaning and downstream consumers of this field are unknown; the input cannot be interpreted as milliwatts from this evidence.

The separate name `RmPmgrPmuOverride` at RVA `0xd1e400` is referenced at `0x8fe700`. After several object-state checks, that code initializes a byte at object `+0x5a8` to 1; if the lookup succeeds and bit 0 of the retrieved value is set, the code writes zero to the byte. The zero byte skips subsequent initialization calls on this path. This identifies a conditional feature-switch behavior, not a method that sets a 90 W reading. Object identity, actual execution, feature meaning, and effects on power protection are unverified. No registry values were written and neither override was tested.

The same initializer registers callback `0x8fdad0`; static disassembly of that callback obtains the `Pmgr`-candidate object from parent `+0x2510` and checks its `+0x5a8` byte before doing further work. If the byte is zero it returns without running that work. In a nonzero branch, after other checks and indirect calls, it passes the 32-bit immediate `0xa7fae0`, the size `0x14a4`, and the descriptor at `Pmgr +0x5c0` to `0x8cfda0`. An earlier version of this note incorrectly called the immediate a function pointer and discussed unrelated code at driver RVA `0xa7fae0`; `mov r8d, 0xa7fae0` does not pass the address of that function. The immediate meaning is not identified. The meanings of the callback, arguments, constants, and affected power behavior remain unidentified. This strengthens the inference that the override gates a Pmgr-associated activity, but it still does not show a 90 W data injection, or establish actual runtime execution or protection effects. No override or callback was invoked.

Further static tracing of `RmPmgrOverride` found that the routine calls a method in the same object's `+0x288` slot immediately after storing the value. The `Pmgr` constructor calls initializer `0x17d6c80`, which sets that slot either to `0xaec020` or the immediate-success stub `0x6170`, depending on a chip selector read from a `GpuHalspecOwner`-shaped object. If the selector is index 46 (`0x2e`), as suggested by the separately observed live GA106 architecture and installed driver's static mapping, the bitmask check at `0x17d7776` selects the stub. The method would then do nothing, but runtime object identity and pointer were not observed, and other consumers of the stored field cannot be excluded. This narrows the immediate call after the override lookup; it does not establish that the setting is globally ineffective or safe. No override was set.
