# Live local-kernel inspection — 8 November 2026

With user approval, Windows Secure Boot was disabled and the current boot entry was set to debug mode. After the user restarted and approved administrator prompts, Microsoft KD connected using local kernel debugging. These were read-only commands; no kernel memory, NVIDIA driver, GPU clocks, or firmware were written. Local kernel debugging does not provide live breakpoints.

The initial `lm` query listed only the kernel; `.reload` populated the module list and showed `nvlddmkm` loaded. `!drvobj nvlddmkm 7` listed seven device objects. A subsequent `!devstack` on `ffff920c094cf030` showed a PCI device instance beginning `PCI\VEN_10DE&DEV_2520&SUBSYS_0A641028&REV_A1`, matching the NVIDIA RTX 3060. The debugger reported its device extension as `ffff920c094cf180`; a short `dq` dump was recorded for further object identification. See [raw output](../runs/local-kernel-gpu-stack-20261108.txt).

All live addresses are specific to this boot and must not be reused after reboot, driver restart, or device removal. The device stack confirms which device was inspected; it does not identify the NVIDIA resource manager's GPU or `Pmgr` object, show the power-control input, or establish an injection method. Secure Boot and kernel debugging should be restored after the investigation, with the user's BitLocker recovery key available.

Follow-up read-only inspection of pointers in the confirmed device stack identified a candidate adapter context at `ffff920c1a90e000` for this boot. It contains the matching vendor/device/subsystem/revision values (`10de:2520`, subsystem `1028:0a64`, revision `a1`) and several function pointers into the loaded `nvlddmkm` address range. This corroborates that the memory belongs to the relevant adapter path; its type and relationship to the `Pmgr` object are not established. The actual kernel escape callback remains unverified, and no memory was modified.

### Installed 610.62 VBIOS-registry gate: static follow-up — 9 November

In installed `nvlddmkm.sys` SHA-256 `a5dde035859cfa298f890c832ae3094002b13a24462ace190da8c2c85ae46142`, the call at `0x6001b3` passes the `vbios` name to helper `0x169380` and sets the GPU-object byte `+0x9af` to 1 on return status zero. The separate initialization path at `0x180ba5` tests that byte and, if nonzero, reads `vbios` through `0xebea0` into a buffer, with length bounds checked afterward. In the primary device-registry branch, `0x169380` invokes `0xebff0`, which supplies callback `0xebfe0` to the common registry routine; that callback copies the first dword from the returned data and returns zero without itself checking the registry type. The common routine's shown post-query path passes the value data to the callback. A nonempty REG_BINARY is therefore a plausible trigger for the gate as well as a source for the later full-buffer read, subject to untraced alternative branches, the Windows registry query's behavior, object identity, initialization order, and other validation. This is a static interpretation, not an observed successful override. ### Firmware virtual-performance-state lead — 10 November

The NVIDIA open-driver reference `src/nvidia/src/kernel/platform/platform_request_handler.c` includes an ACPI platform-request handler for BIOS-requested virtual performance-state limits. Its command IDs for virtual-state information, mapping, and setting are `0x20800ad4`, `0x20800ad5`, and `0x20800ad6`. A read-only static scan of this machine's installed Windows driver (SHA-256 `a5dde035859cfa298f890c832ae3094002b13a24462ace190da8c2c85ae46142`) found these as instruction immediates at RVAs `0x629132`, `0x628d2c`, and `0x628cad`. In the last two cases the same Windows function beginning at RVA `0x628c01` uses different request-type branches, extracts a byte after shifting by 8 and passes the corresponding identifier to an indirect call. This resembles the reference platform request mechanism; it does not establish that the code executed on this laptop, that its firmware supports the mechanism, that virtual state maps directly to NVAPI P5, or that it causes the current memory behavior. No command was sent and no setting changed. The reference itself cautions that some slow-virtual-state notions do not apply to newer P-state implementations.

Windows' `GetSystemFirmwareTable` enumeration did not list DSDT, but a separate read-only registry check did find a 308114-byte Dell DSDT under `HKLM\HARDWARE\ACPI\DSDT\DELL__\Dell_Inc\20170001`. A raw-byte scan did not find the NVIDIA reference GPS, NVHG, or NVPCF GUID byte sequences in that DSDT. This narrow negative is not proof the machine lacks the interface: SSDTs and indirect AML references were not decoded or searched comprehensively, and firmware may encode or expose identifiers differently. No ACPI method was invoked.

The accessible registry DSDT/SSDT subtree contained only two binary table values; neither contained those three raw GUID byte patterns. Other SSDTs were visible through firmware-table enumeration but not individually available through that registry scan, so this is not a comprehensive firmware search. Separately, the open NVIDIA reference defines a RATED_TDP status structure showing arbitration among client requests and a virtual-state output. That structure's rated-TDP/turbo virtual states are distinct concepts from the public NVAPI P0/P5 states; the existence of the status structure does not establish it is supported by this Windows driver or determines P5. No driver commands or firmware methods were issued.

The read-only channel captures expose a further difference between the previously booted 6.1 W-only image and the slope image: derived C12 changed from [230409, 10875, 21187000] to [7872, 1077, 7309000]. Numerically, 230409/10875 is approximately 21.187 and 7872/1077 approximately 7.309, consistent with the third word being computed from the first two under the inferred mW/mA/µV units. The 6.1 W-only image already rewrote C12 as C3+C10; scaling C3 then changes this derived result. Thus the apparent 7.3 V input may be an artifact of combining manipulated channel values, not an independent voltage measurement. Whether any controller consumes C12, and whether it contributes to P5, remain unproven. This suggests comparing alternative relationships offline rather than asserting the physical input fell to 7.3 V. No configuration was changed.

Offline modeling against the hash-checked current-slope image found that C12's range could be narrowed from relations 13–14 to relation 13 alone, leaving the C3 and C5 slope edits untouched. Relation 13 refers to C3 with unit weight. Using the captured C3 words 1772 and 77, a simple ratio predicts roughly 23.0 V instead of 7.3 V; the 6.1 W-only run already demonstrated that calculated voltage need not equal the source's voltage field, and rounding or different firmware semantics could change the result. This would also change C12's power/current outputs and any policies that consume them; it would not establish real protection, an actual input voltage, PMU acceptance, or P5 causation. No image was created, staged, or tested.

Inspection of all 20 records in the saved version-0x30 policy table found row 1 has first bytes `04 0c`: under the previously inferred flags/channel interpretation, a class-4 policy names C12. No other record's second byte equals 12. This is a concrete possible policy consumer of C12, not proof that the installed driver activates row 1, how class 4 operates, or that it controls P5. The older nvgpu parser handles class-5 hardware-threshold entries and does not validate class-4 semantics for this image. Consequently, changing C12 could affect a policy and cannot be treated as a cosmetic voltage-only change.

The existing read-only kernel snapshot taken during the prior 6.1 W-only boot ([R1](../runs/local-kernel-6100-live-policies-20261109.txt)) shows that row 1 had a non-null live driver object. This supports that the driver constructed the row and preserved a C12-like reference; it does not establish firmware activation, its units or actual control decision, and that snapshot predates the slope-image boot. No addresses from the earlier boot were reused and no live setting changed.

The Vix parser's power-row conventions interpret flag `0x04` as class 4 with a milliwatt limit, not a voltage-specific limit. Applying its conventional dword offsets to row 1 yields 1, 1001000, and 1001000, nominally 0.001/1001/1001 W if these conventions apply. Vix's corresponding class-4 handling is based on other supported board shapes and explicitly excludes notebook power for that particular connector decoder, so it cannot validate this notebook policy's exact meaning. Correction: the earlier note incorrectly attributed the 5,000,000 dword from R0 to R1. R1's prior snapshot actually contains `0x000f4628` (1,001,000) at multiple limit-like positions, matching the row-1 VBIOS value; this correspondence supports propagation of that value but does not establish units, a currently active threshold, or voltage protection. This weakens the claim that computed 7.3 V itself is a direct trigger; the row may instead be concerned with power. No comparison to P5 control has been established.

If C12's first word and row 1's rated value are comparable power values in identical units, the slope-image reading 7,872 is only 0.786% of the 1,001,000 rated value. That makes an ordinary upper power threshold on that observed field a weak explanation for P5, conditional on that interpretation. It does not exclude a minimum-voltage condition, a different input, different policy semantics, firmware-side values or other constraints. The calculation does not justify changing the policy or the C12 relationship without stronger evidence.
