# REA decompilation of a power-query handler — 8 November 2026

REA 6.7.0 using Ghidra 12.1.4 decompiled the installed Windows `nvlddmkm.sys` SHA-256 `a5dde035859cfa298f890c832ae3094002b13a24462ace190da8c2c85ae46142`, virtual address `0x1404e4d50` (RVA `0x4e4d50`). Complete REA output and limitations are preserved in [the evidence record](../runs/rea-power-handler-0x4e4d50-20261108.json). This target corresponds to the candidate `0x2080a613` RM dispatch entry identified earlier; runtime dispatch to this specific implementation is not established.

The decompiler shows that the function accesses an object at a parent offset `0x2510`, copies four header fields to its output, obtains entries from an object at offset `0x5e8` through a function pointer at `0x628`, and invokes another indirect method for each entry to populate output. This narrows a candidate query-response path to its object dispatch, but provides neither the ultimate source of the readings nor an identified controller input. The output record is not evidence of a fixed-power write interface. This is pseudocode, not NVIDIA source, and structure types and method targets are unknown. The import was read-only and ephemeral; the original driver was not modified.

The related average-query candidate handler at RVA `0x4f06d0` was independently decompiled using the same driver and provider; its [complete REA evidence](../runs/rea-average-power-handler-0x4f06d0-20261108.json) identifies the same access chain through `param_1 + 0x158`, `+0xe0`, and object pointer `+0x2510`. It then reads a different member at `+0x5a0`, checks a separate object and state byte, and invokes an indirect method to populate the output. The shared parent is evidence of a common object layout for these two static handlers, not proof that the methods share a physical sensor, run for the live query, or drive GPU boost. The distinct fields give a more focused target for tracing the parent class and runtime method implementations.

## Shared-object class identification

Read-only disassembly on the same driver found initialization code at RVA `0x1196f0` passing the address of the parent object's `+0x2510` slot and class ID `0x894574` to helper `0x119c80`. The helper searches a table using that ID and ultimately writes an acquired object pointer to the supplied slot at `0x119e12`. NVIDIA's nearby open-source generated [`g_eng_desc_nvoc.h`](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/610.57.04/src/nvidia/generated/g_eng_desc_nvoc.h) names class ID `0x894574` `Pmgr`. The shared offsets, code shape, and matching class ID make the power-manager identity a strong static inference. Runtime identity, the implementation behind its two indirect query methods, and whether either method feeds the boost controller remain unverified. This narrows the next investigation to `Pmgr` and its members rather than establishing a spoof interface. No GPU state was modified.

## Candidate average-query object construction

In a further read-only trace, code at RVA `0x4f0320` treats its second argument as the object holding the `+0x5a0` member. Under two checks on a separate parent object, it calls factory `0x917b10` and stores the returned pointer at `+0x5a0` at `0x4f03f5`. This matches the member read by the average-query candidate handler. The factory passes constructor callback `0x917a80` to `0xbc8c40`; the callback enters `0x917be0`. The latter calls `0xbf8100`, resolves an interface through a guarded indirect call, and installs a method pointer to `0x917d90` at interface offset `+0x08`. The average-query handler also resolves an interface and calls its `+0x08` method. These static patterns suggest `0x917d90` as a candidate implementation for further tracing, but do not prove the same interface or actual runtime target: the factory's arguments, object identity, later method overwrites, gates, and cast results need confirmation. Method `0x917d90` delegates to `0xbf83f0`, which in turn calls `0xc62f20` and, after a pointer check, `0xbbc9a0`. Those callees are next trace targets. None of this establishes that the query response controls boost or accepts an injected wattage; no code or GPU state was changed.

Follow-up static disassembly shows `0xbbc9a0` compares adjusted object pointers and returns a status; the inspected path does not itself read a sensor or insert a wattage. `0xc62f20` resolves an adjusted object through `0x5a2ae0`, calls `0x7eba60`, and on success copies a two-byte and one-byte field to its output. `0x7eba60` copies a byte, calls an indirect method from the resolved object at `+0x58`, then iterates entries using a method at `+0x40`; for each entry it obtains an output location through another indirect call and invokes a method at entry `+0x08`. This follows the candidate query's data assembly further but leaves the runtime method targets and units unknown. The `0x917d90` relationship is still conditional on the unverified interface resolution described above. Do not infer an injection point or a controller connection from the output assembly alone.

The first REA attempt exceeded its 330-second startup limit; a second with `REA_GHIDRA_STARTUP_TIMEOUT_MS=1200000` succeeded. REA's Codex registration was refreshed with a recovery backup, using the existing Node 24 runtime and a separately installed Ghidra 12.1.4 archive whose SHA-256 matches the official release. A client restart is required before assuming the newly registered MCP tools are connected; this result came from the REA CLI.
